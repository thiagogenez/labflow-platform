# Decisions

Settled on 2026-11-18 while planning the reboot. Each line is a decision and its main reason. Reopen a decision explicitly before changing it, and record the change here.

## Repositories and Process

| ID | Decision | Why |
| --- | --- | --- |
| D01 | Delete and recreate the repository; discard the previous domain-model work. | Force-pushing would keep old commits reachable through closed pull requests. |
| D02 | Two repositories: `labflow` (application code, images) and `labflow-platform` (IaC, GitOps, docs). Linked by image-digest pull requests, not Git submodules. | Separate access, deploy without rebuild, no CI loops, a clean deploy history. Submodules couple versions at the Git level. |
| D03 | One pre-commit configuration per repository, identical locally and in CI, with commit-message checks. | The editor, the hook and CI must reject the same things. |
| D04 | Conventional Commits; subject at most 72 bytes; unwrapped body paragraphs; no co-author trailers or "Generated with" lines in commits and pull requests. Pull requests merge with a merge commit titled by the pull request; no squash, no rebase. Every commit and pull request references a labflow-platform issue, automated ones such as digest promotion included. Amended 2026-11-19: ticket references and pull request checks. | Clean, readable history in public portfolio repositories; every change traces back to its ticket; signed commits stay intact and each pull request remains one revertible unit. |
| D05 | The agent writes code and infrastructure drafts and, once the learner approves the text, commits, pushes topic branches and opens pull requests; the learner runs the key commands, writes one small piece per day, owns design calls and merges. | Fifteen days are not enough to type everything by hand; running and breaking it is where the learning is. |
| D06 | README as portfolio: Mermaid diagrams, generated animated SVG with static fallback, honest status table. Docs live in `labflow-platform`. | The platform is the focus; animations stay sharp, small and theme-aware. |
| D07 | Three interview questions per day in English; mock interview on Day 15. | Target: Senior Platform Engineer, SRE and Kubernetes roles, interviewed in English. |
| D08 | Every commit passes three independent agent reviews (correctness and duplication; over-engineering; security and operability), two rounds each; findings are compared for consensus and the learner decides. Amended 2026-11-19: review stops when a round raises no high or medium finding, with at most two full rounds per change. Amended 2026-11-20: reviewer A runs on a different model (Codex) for model diversity. Amended 2026-11-22: an applied high or medium code finding comes with a regression test that fails without the fix, confirmed by mutation; each pull request keeps a ledger per reviewer; a seeded-bug benchmark at the end of #8 measures each reviewer. | Clean, DRY, right-sized code in public repositories; independent reviewers catch different problems. A finding is proven only by a test that fails without its fix, and a reviewer is judged by the bugs it catches. |

Amended 2026-11-20: adds `supplier-simulator` (D63). | Polyglot like real companies; Go on the hot path, Python for workers and data. |

Reopened 2026-11-18: AWS moved from self-hosted brokers to native SNS + SQS. | Measure before choosing; publishing an event to two brokers only adds failure modes. |

| D14 | Shipping quotes from `shipping-api` with a timeout and a flat-rate fallback. Refined 2026-11-20 by D55. | Exercise timeouts, retries, circuit breaking and graceful degradation. |
| D15 | Database per service on one CloudNativePG cluster; active-passive. | Service ownership without the cost of one cluster per service. Active-active is a separate project. |
| D16 | Valkey for the server-side cart, catalog cache and the gateway's global rate limit. | Concrete use cases; BSD licence; Redis protocol. |
| D17 | No extra NoSQL store; ClickHouse is a stretch goal. | No real use case justifies the memory and time. |
| D47 | Events are CloudEvents 1.0 in structured JSON mode, the same JSON on every broker; `type` is `labflow.<aggregate>.<event>.v<major>`, and `subject` is the order ID, repeated from `data` so logs and dead-letter tooling never read `data`. One closed JSON Schema per type, checked by producer tests; consumers never validate, ignore unknown fields and tolerate unknown enum values; fields are added as optional, and an incompatible change is a new major `type` published alongside the old one (#26). Settled 2026-11-20. | A CNCF standard instead of a home-made envelope; contract breaks are caught in CI, not in production. |
| D61 | Tracing: the W3C `traceparent` carries the trace context in HTTP headers and events, and its trace ID is the log correlation ID; public entry points start a new trace, and consumers process an event as a child of its `traceparent`. Every service runs the OpenTelemetry SDK; Docker Compose sends traces to Jaeger, the private cluster to Tempo if it stays (D44), and elsewhere the exporter is off (`OTEL_TRACES_EXPORTER=none`). Settled 2026-11-20. | One trace ID per request ties the logs of every service together; a client must not choose our correlation ID. |
| D48 | Transactional outbox in the Debezium Outbox Event Router table shape (`aggregatetype` is the producer's topic, `aggregateid` the order ID), published by an in-process polling relay that takes a PostgreSQL advisory lock per batch, so one relay per service is active. Settled 2026-11-20. Amended 2026-11-23: the relay and the RabbitMQ publisher live in `libs/go`, shared by every producer. Each batch is published confirmed and `mandatory` (D49) inside the transaction that holds the advisory lock and locks the batch's rows; only events the broker accepted are marked published. A batch has 10 seconds and stops publishing 3 seconds before its end, leaving time to commit the marks; if the commit fails anyway, the events are published again and consumers deduplicate them. When publishing runs out of time, the publisher closes its TCP socket, which frees every call a hung or alarmed broker never answers, so it can ignore blocked-connection notices. A separate loop refreshes the gauges every 5 seconds and deletes old rows (D64). Checkout never waits for the broker: `/readyz` checks only PostgreSQL, and D44 alerts on the backlog and on RabbitMQ's alarms. | The simplest relay, identical on every broker and without extra infrastructure; the table shape keeps change data capture open as the scaling path. A broker outage must not stop sales; a relay stuck on a hung broker would hold the lock every replica needs. |
| D49 | Delivery is at least once and unordered. Consumers are idempotent, tolerate reordering, and retry a missing prerequisite with backoff up to a limit before dead-lettering it: RabbitMQ quorum queues get a dead-letter exchange, an explicit delivery limit and at-least-once dead-lettering (`dead-letter-strategy=at-least-once`, `overflow=reject-publish`), and Kafka retries never block a partition. Queues, bindings and topics exist before producers run; RabbitMQ publishes are `mandatory`, so an unroutable message is a failure, and Kafka consumers start from the earliest offset. Settled 2026-11-20. | Competing consumers (KEDA), SQS Standard, retries and separate topics all reorder events; per-order ordering holds only within one Kafka partition or SQS FIFO message group and needs a single active consumer per RabbitMQ queue; unbounded retries stall partitions or silently drop messages. |
| D62 | Broker topology: Kafka has one topic per producing service (`orders`, `payments`, `inventory`) keyed by order ID; RabbitMQ has one topic exchange, the event type as routing key and one quorum queue per consuming service; SNS + SQS is laid out on Day 12 with raw message delivery, so consumers receive the same JSON. Each service may write only to its own topic or routing keys (Kafka ACLs, RabbitMQ topic permissions, SNS topic policies), and consumers accept each event type only from its producer's topic or routing key; on AWS, where raw delivery drops the topic, each subscription filters on `type` and each queue policy admits only the approved topics. Settled 2026-11-20. | The same envelope and keys on every broker; `source` is self-asserted, so the broker must stop one service from forging another's events. |
| D50 | Event catalogue v1: from order-api `order.placed`, `order.payment_failed` (consumed only by email-worker), `refund.requested`, `refund.completed` and `refund.failed` (consumed only by email-worker), every one that leads to a customer email carrying the customer's email and first name; from payment-api `payment.refunded` and `payment.refund_failed` (consumed only by order-api) and `payment.late_charge_refunded` (consumed by order-api and email-worker); from inventory `inventory.allocated` (one per order, with allocated and backordered quantities per line) and `inventory.backorder_allocated`. Settled 2026-11-20. | Each event comes from the owner of its facts; order-api owns refunds, so their details are published once; inventory and analytics act only on placed orders and skip the rest without storing or logging its payload. |
| D51 | Checkout saves the order as `pending_payment`, charges through payment-api with the order ID as idempotency key, then marks it paid and writes `order.placed` in one transaction: 201 paid, 402 declined, 202 still pending. A reconciler reads the charge's current state from payment-api and resubmits only when payment-api has no record of it; after 15 minutes unresolved, order-api asks payment-api to cancel the charge and follows its answer: a charge that already succeeded takes the paid path, a recorded cancellation fails the order, and an unanswered cancellation stays under reconciliation. An order that answered 202 and then fails emits `order.payment_failed`, so the customer is emailed; payment-api refunds any charge that succeeds after its cancellation and emits `payment.late_charge_refunded`. Settled 2026-11-20. | A crash or outage between charge and commit must neither lose a paid order, charge twice, nor keep money for a failed order; an idempotent replay may return a stale first response. |
| D52 | Stock is allocated asynchronously from `order.placed`, without reservation; shortfalls become first-in, first-out backorders, and goods receipts enter through an idempotent inventory API. Settled 2026-11-20. | A synchronous reservation adds coupling and a failure point to checkout. |
| D63 | Automatic replenishment: an (s, Q) reorder-point policy sends purchase orders to `supplier-simulator`, a simulated external supplier (#24). Settled 2026-11-20. | Load tests drain stock; a real shop restocks from its suppliers. |
| D53 | Refunds refine D13: within 30 days of payment, per line and quantity, requested with the order access token (D56); completed and in-flight refunds per line never exceed what was bought; VAT is returned proportionally: a refund's gross is the unit price times its quantity, its VAT is the line's VAT for the cumulative refunded quantity, rounded, minus the VAT already refunded, and its net is gross minus VAT, so the last unit takes every remainder; shipping is returned only when the whole order is refunded; requests on one order are serialised and return 202. order-api owns the saga and emits `refund.completed` once payment-api reports the money moved; inventory first cancels the line's open backorder and restocks only allocated units, assuming resellable returns. A refund unanswered between services is resent after 10 minutes, three times, then alerts; one pending at the provider for more than 5 days alerts; a final refusal emits `refund.failed`, so the customer is emailed, and alerts the team, which refunds by bank transfer with the customer's agreement and records it through an internal, idempotent order-api endpoint with no public route; order-api then emits `refund.completed` once, as for any refund. Settled 2026-11-20. | These are lab rules: 30 days counts from payment because fulfilment is out of scope, whereas the EU withdrawal period for goods runs 14 days from delivery; the EU 14-day reimbursement deadline bounds how long a refund may stay stuck. |
| D54 | Money is integer minor units with an ISO 4217 currency, EUR only. Prices include VAT; every order and refund line stores its rate and its net, tax and gross amounts, rounded per line, and totals are the sums of the lines and shipping. The shop is a fictitious German company charging each product's German VAT rate on EU sales, under the distance-sales threshold described below; the One-Stop Shop is a production gap. Analytics revenue is net of VAT. Settled 2026-11-20. Amended 2026-11-23: each product carries its German VAT rate, 19 % standard or 7 % reduced (books and the other goods of Annex 2 UStG); shipping, an ancillary service, follows its goods: its gross is split across their rates in proportion to the goods' gross per rate with exact integer arithmetic, each share floored and the leftover cents going by descending remainder, ties to the higher rate, so equal remainders are resolved consistently; each share is taxed once at its rate and stored, so D53's final shipping refund returns those amounts. Before its first producer ships, `order.placed.v1` is revised in place: shipping keeps its zone, speed, rate source and total amounts and replaces its single rate with a per-rate breakdown; producer tests check that the parts add up to shipping and the lines plus shipping to the totals; D47 governs every change after that. The distance-sales threshold holds only while EU distance sales stay at or below EUR 10,000 in both the current and the previous calendar year (§ 3c (4) UStG). | Retrofitting tax into a money model is expensive; per-line rounding with cumulative refund allocation never returns more than a line holds. |
| D55 | shipping-api quotes from rate cards by zone (`DE`, `EU-1` to `EU-3`), speed (standard, express) and weight band; order-api quotes server-side at checkout, with a timeout well inside the 500 ms checkout p95, and falls back to D14's flat rate on timeout or error. Settled 2026-11-20. | Prices from the browser are never trusted. |
| D56 | Guest checkout: the order access token is the HMAC-SHA-256 of the order ID under a key that order-api and email-worker read from Vault (Secrets Manager on EKS), so an idempotent replay returns it and the confirmation email carries a long-lived link to the order page without storing it. Links carry it in the URL fragment and the storefront sends it in a header; it never enters events, outbox rows, idempotency records or logs. Rotating the key invalidates every link. Settled 2026-11-20. Amended 2026-11-23: the token is the HMAC-SHA-256 over the UTF-8 bytes of the lowercase, hyphenated order UUID, encoded as unpadded base64url; a shared test vector (key, order ID, token) runs in both the Go and the Python tests. | Order IDs leak through logs and URLs; a derived token survives a lost response and reaches the email without travelling through the broker. |
| D64 | Personal data: events carry only the customer's email and first name; every store (queues, retry and dead-letter queues, Kafka `retention.ms` plus `segment.ms`, published outbox rows) keeps an event for at most 7 days, and processing ends 7 days after the event's `time`, so a redrive never extends it; SNS retries towards an unavailable SQS queue are the one AWS exception. Among consumers only email-worker stores the contact, deleting it 60 days after payment or failure, or when the order's last backorder closes, whichever is later; an email whose contact is gone is not sent and alerts the team; analytics stores no personal data. Erasure on request is a production gap. Settled 2026-11-20. Amended 2026-11-23: 7 days is each store's retention target, counted from when the event enters it, but on RabbitMQ the outbox and the consumer's queue share one budget. The relay selects for publishing only events at most 7 days less one hour old, and sets the rest of their 7 days, counted from the row's creation when the batch is selected, as the message expiration. From that age an event is due for deletion: unpublished ones are tried every 5 seconds, published ones every 30 minutes. A message that is dead-lettered (expired, rejected or out of deliveries) spends up to 7 more days in its dead-letter queue, so an event normally exists at most about 14 days after its `time`. It stays longer while its dead-letter queue cannot take it, since at-least-once dead-lettering then keeps it in the source queue; and RabbitMQ expires a message only at the head of its queue, so behind fresher messages in a stopped consumer's queue it may wait for that queue's own 7 days, about 21 days in all. A redrive (D44) returns a message to its source queue only, with the rest of 7 days from its `time` as its expiration. Consumers skip and count an event older than 7 days. Database backups and WAL archives keep outbox rows for their own retention (D30), as they keep the orders (D66). | Broker logs cannot erase single records; a contact must outlive the latest email it serves. A dead-lettered message loses its expiration, so its dead-letter queue starts a new 7 days; the hour covers the sweep interval and the seconds between an event's `time` and its row. |

Settled 2026-11-20. Amended 2026-11-23: Jinja2 renders email templates; testcontainers-python runs the Python integration tests; santhosh-tekuri/jsonschema validates events in Go producer tests; Go integration tests also run against a real RabbitMQ in a throwaway container (`libs/go/rabbitmqtest`), loaded with Docker Compose's definitions file. | Shared code earns its place at the third consumer (D18); recorded library choices answer "why this one"; migrations at startup race between replicas and block rollbacks. Mocked databases and brokers miss constraint, locking and timeout behaviour; documentation that a gate does not check decays. |
| D58 | The storefront is static HTML and JavaScript served by unprivileged nginx, which also proxies `/api` in Docker Compose in place of the gateway. The fictitious catalogue holds laboratory and technical-office products, a few of them low on stock. Settled 2026-11-20. | D60 | An order holds at most 50 lines of at most 99 units each, enforced at checkout and in the event schema; amounts stay at or below 2^53 - 1. Settled 2026-11-20. | An unbounded order makes an event larger than SNS accepts by default (256 KiB; at most 1 MiB when raised) and blocks the outbox behind it; larger integers lose precision in JSON parsers (RFC 7493). |
| D65 | psp-simulator, a simulated external card processor, validates card details as a processor does before it issues a token: the Luhn check digit, the Visa, Mastercard and American Express prefixes and lengths, an expiry from the current month to December twenty years ahead, and a CVC of 3 digits (4 for American Express). It keeps the brand, the last four digits and the simulated outcome, never the full number, expiry or CVC. Fictitious test BINs choose the outcome: a brand prefix (`400000`, `510000`, `370000`) followed by `00` approve, `95` decline, `10` slow approval, `30` pending then approved, or `31` pending then declined; any other valid number is approved. Its `cards` command prints a valid test card for a chosen brand and outcome. Settled 2026-11-21. | Realistic validation exercises the errors order-api and the storefront must handle; deterministic outcomes make every payment path reproducible on demand, as real processors' test cards do. |
| D66 | Checkout: `POST /v1/quotes` prices lines (SKU and quantity), a destination country and a shipping speed without storing anything. `POST /v1/orders` takes a quoted `Idempotency-Key` and a JSON body with `customer {email, first_name, last_name}`, `shipping_address {line1, line2, postal_code, city, country}`, `shipping_speed`, `lines [{sku, quantity}]`, `payment_token` and `expected_total`, the gross total the customer was shown. It answers 400 for control characters in customer text, an email over 254 characters or outside the event contract's format, a name, address line or city outside 1 to 100 characters (line2 may be empty), a postal code outside 1 to 16 characters, a country outside D67, a speed other than `standard` or `express`, an empty or over-255-byte payment token, an `expected_total` outside 1 to 2^53 − 1 cents, or anything but 1 to 50 lines of 1 to 99 units each (D60); a quote and an order validate lines, destination and speed alike, and a retired or unknown SKU can be neither quoted nor ordered. order-api prices the lines from its catalogue (D68) and their VAT under D54; shipping uses D67's configured rate until shipping-api arrives, then a D55 quote with that rate as fallback. order-api first looks the idempotency key up on its orders, where it stays for the order's life, beyond D57's 24 hours: a different fingerprint gets 422, and a match resumes D51 from the saved order, token and prices, even after the shared middleware releases the key on a server error, so a late retry never creates a second order. Only a new checkout checks the catalogue and `expected_total`: if the total differs, it answers 409 `price_changed` as an RFC 9457 problem carrying the new quote in the shape of `POST /v1/quotes`, creates no order and charges nothing, so the customer pays only a total shown right before the order button (§ 312j BGB); the storefront shows the new total and, once the customer confirms, sends it under a fresh key. The pending order, its prices, the key and the fingerprint are committed together before the charge. It answers 201 paid, 202 pending, or 402 declined as an RFC 9457 problem; each carries the order and its access token (D56), which the stored idempotent response never holds: it is derived again for every answer, replays included. `GET /v1/orders/{id}` takes `Authorization: Bearer <access_token>`, compares it in constant time, answers 404 to a wrong token and an unknown order alike, and sends `Cache-Control: no-store`. The address stays in order-api, out of events, logs, traces and other services; how long order-api keeps it with the customer's name and email (commercial and tax law for paid orders, prompt deletion for failed ones under the GDPR) is a production gap. The server-side cart and the catalogue cache in Valkey (D16) arrive with the storefront. Settled 2026-11-23. | Order APIs take line items, with the cart as a layer before them; a new order ID on retry would be a new charge idempotency key (D51): a second order, charged twice with a reusable payment method, or failed with a single-use token; the confirmation link carries the token in its URL fragment and the storefront sends it in the Authorization header, keeping it out of request targets and access logs. |
| D67 | The shipping zone comes from the address's country: `DE` Germany; `EU-1` AT, BE, CZ, DK, FR, LU, NL, PL; `EU-2` ES, FI, HU, IE, IT, PT, SE, SI, SK; `EU-3` BG, CY, EE, GR, HR, LT, LV, MT, RO; any other country is rejected. D14's flat rate lives in order-api's configuration per zone and speed, gross, in EUR, initially DE 5.90 standard and 12.90 express, EU-1 9.90 and 19.90, EU-2 12.90 and 24.90, EU-3 15.90 and 29.90. Settled 2026-11-23. | Zones follow distance, as German parcel carriers price them; rates change without a release. |
| D68 | The catalogue lives in order-api's database and loads from a versioned file through `catalogue import`, a job run with order-api's data role, not the migration owner. It validates the whole file against the `order.placed` limits (SKU pattern and length, name length) and D54's amounts and rates, then, in one transaction serialised against other imports by an advisory lock, upserts by SKU and retires the products missing from the file, which stay for past orders but are no longer listed or sold. A product has a SKU, a name, a positive gross unit price in cents, a VAT rate and a per-unit weight in integer grams; a shipment weighs the sum of weight times quantity. `GET /v1/products` lists the products on sale. An internal catalogue API waits for a caller (#32). Settled 2026-11-23. | Reference data changes without a schema migration or a code release; the import and the future API share one write path that keeps every product on sale within the event contract. |
| D69 | email-worker sends English email from `LabFlow <orders@labflow.example>` only through Mailpit, the lab's simulated mail server, with SMTP relaying and forwarding both disabled, so no email leaves the lab; Jinja2 renders the text and HTML alternatives, autoescaping the HTML. For each event ID a worker atomically claims the send (`sending`, with an expiry longer than the SMTP timeout), calls SMTP, records `sent` only while it still owns the claim, and only then acknowledges the delivery. A redelivery skips a `sent` email and waits on a live claim, so only one worker owns it, although a sender that pauses past the expiry can still resume; it takes over an expired claim and sends again with the same `Message-ID`, derived from the event ID, counting the resend attempt in a metric. A pause or crash between SMTP acceptance and the `sent` record may therefore duplicate an email, but never loses one within D64's processing deadline. Settled 2026-11-23. | SMTP has no idempotency key, so exactly-once email is impossible; a lost confirmation costs more than a rare duplicate, which mail clients recognise by its `Message-ID` and the metric makes visible. |
| D70 | RabbitMQ's vhost, exchange, quorum queues, dead-letter queues, bindings, policies, users, permissions and topic permissions come from a definitions file loaded at boot in Docker Compose, and from Messaging Topology Operator objects reconciled from Git on the clusters, changed and rolled back through pull requests. Policies, not queue arguments, set dead-lettering, the delivery limit and overflow (D49); the application `Vhost` and its `Queue` objects use `deletionPolicy: retain`, so deleting or pruning them never deletes a queue with its messages; an intended removal drains the queue first. Each producer may only write to the exchange, within D62's routing keys, and each consumer may only read its own queues, never configure, so no service can declare, delete, bind or unbind anything. A topology object that is not Ready alerts. In Compose the boot import only adds, so an object removed from the file is then deleted by hand through RabbitMQ's administration, after draining its queue. Settled 2026-11-23. Amended 2026-11-23: the vhost is `labflow` and D62's topic exchange is `labflow.events`. Each consumer's quorum queue is named after it and dead-letters, with the consumer's name as routing key, through the direct exchange `labflow.dead-letter` to the quorum queue `<name>.dead-letter`. A per-consumer policy sets D49's dead-lettering with `max-length` 100000, `delivery-limit` 5 and `message-ttl` 7 days; the dead-letter queues' policy sets the same `reject-publish` overflow, length and TTL. A consumer's user arrives with the service, its queues with the first event routed to them. order-api may write only routing keys starting `labflow.order.`; the permission adds `labflow.refund.` before order-api writes its first refund event, since a refused routing key closes the publishing channel and fails the batch again on every retry. In Docker Compose, RabbitMQ has a fixed hostname, since it keeps its data under its node name. It is told the container's memory limit, which it does not read, and raises its disk alarm, which blocks publishers, below 1 GB free; on the clusters the disk limit is at least the memory watermark. In Compose, `definitions.template.json` holds the users, `admin` among them, and their passwords are filled in per environment (D40). The clusters define no administrator in Git: the Cluster Operator's default user, an administrator the Topology Operator uses, takes its credentials from a Secret (D40) that only the admin persona (D42) may read. | D49 needs the topology to exist before producers run; a service that could bind or unbind could silence another's events or receive events D50 does not give it. |
