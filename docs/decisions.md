# Decisions

Settled on 2026-11-18 while planning the reboot. Each line is a decision and its main reason. Reopen a decision explicitly before changing it, and record the change here.

## Repositories and Process

| ID | Decision | Why |
| --- | --- | --- |
| D01 | Delete and recreate the repository; discard the previous domain-model work. | Force-pushing would keep old commits reachable through closed pull requests. |
| D02 | Two repositories: `labflow` (application code, images) and `labflow-platform` (IaC, GitOps, docs). Linked by image-digest pull requests, not Git submodules. | Separate access, deploy without rebuild, no CI loops, a clean deploy history. Submodules couple versions at the Git level. |
| D03 | One pre-commit configuration per repository, identical locally and in CI, with commit-message checks. | The editor, the hook and CI must reject the same things. |
| D04 | Conventional Commits; subject at most 72 characters; unwrapped body paragraphs; no co-author trailers or "Generated with" lines in commits and pull requests. Pull requests merge with a merge commit titled by the pull request; no squash, no rebase. Every commit and pull request references a labflow-platform issue, automated ones such as digest promotion included. Amended 2026-11-19: ticket references and pull request checks. | Clean, readable history in public portfolio repositories; every change traces back to its ticket; signed commits stay intact and each pull request remains one revertible unit. |
| D05 | The agent writes code and infrastructure drafts and, once the learner approves the text, commits, pushes topic branches and opens pull requests; the learner runs the key commands, writes one small piece per day, owns design calls and merges. | Fifteen days are not enough to type everything by hand; running and breaking it is where the learning is. |
| D06 | README as portfolio: Mermaid diagrams, generated animated SVG with static fallback, honest status table. Docs live in `labflow-platform`. | The platform is the focus; animations stay sharp, small and theme-aware. |
| D07 | Three interview questions per day in English; mock interview on Day 15. | Target: Senior Platform Engineer, SRE and Kubernetes roles, interviewed in English. |
| D08 | Every commit passes three independent agent reviews (correctness and duplication; over-engineering; security and operability), two rounds each; findings are compared for consensus and the learner decides. Amended 2026-11-19: review stops when a round raises no high or medium finding, with at most two full rounds per change. Amended 2026-11-20: reviewer A runs on a different model (Codex) for model diversity. | Clean, DRY, right-sized code in public repositories; independent reviewers catch different problems. |
| D09 | When a decision is unclear, the agent runs the grilling skill instead of guessing. | Decisions stay with the learner and get recorded. |
| D18 | labflow-platform holds the single contribution guide and backlog for both repositories; small per-repository checks stay copied until a third consumer justifies a shared action. Settled 2026-11-19. | One place to read rules and file work; the rule of three keeps shared abstractions earned. |

## Application

| ID | Decision | Why |
| --- | --- | --- |
| D10 | Thin but realistic application in Go (order-api, payment-api, inventory, psp-simulator) and Python (shipping-api, email-worker, analytics-worker), plus a static storefront. Amended 2026-11-20: adds `supplier-simulator` (D63). | Polyglot like real companies; Go on the hot path, Python for workers and data. |
| D11 | One broker adapter per language (RabbitMQ, Kafka, SNS + SQS); one broker per deployment: Kafka and RabbitMQ stressed on the private cluster, native SNS + SQS on AWS. Reopened 2026-11-18: AWS moved from self-hosted brokers to native SNS + SQS. | Measure before choosing; publishing an event to two brokers only adds failure modes. |
| D12 | Payments through `psp-simulator`, a black-box stand-in for Stripe: browser tokenization, idempotent charges, signed asynchronous webhooks that can arrive duplicated, late or out of order. | Real integrations work this way; card numbers never reach the backend. |
| D13 | Refunds: full or per-item partial, within 30 days, idempotent, as a choreographed saga. Refined 2026-11-20 by D53. | Real return flows; saga versus two-phase commit is a common interview topic. |
| D14 | Shipping quotes from `shipping-api` with a timeout and a flat-rate fallback. Refined 2026-11-20 by D55. | Exercise timeouts, retries, circuit breaking and graceful degradation. |
| D15 | Database per service on one CloudNativePG cluster; active-passive. | Service ownership without the cost of one cluster per service. Active-active is a separate project. |
| D16 | Valkey for the server-side cart, catalog cache and the gateway's global rate limit. | Concrete use cases; BSD licence; Redis protocol. |
| D17 | No extra NoSQL store; ClickHouse is a stretch goal. | No real use case justifies the memory and time. |
| D47 | Events are CloudEvents 1.0 in structured JSON mode, the same JSON on every broker; `type` is `labflow.<aggregate>.<event>.v<major>`, and `subject` is the order ID, repeated from `data` so logs and dead-letter tooling never read `data`. One closed JSON Schema per type, checked by producer tests; consumers never validate, ignore unknown fields and tolerate unknown enum values; fields are added as optional, and an incompatible change is a new major `type` published alongside the old one (#26). Settled 2026-11-20. | A CNCF standard instead of a home-made envelope; contract breaks are caught in CI, not in production. |
| D61 | Tracing: the W3C `traceparent` carries the trace context in HTTP headers and events, and its trace ID is the log correlation ID; public entry points start a new trace, and consumers process an event as a child of its `traceparent`. Every service runs the OpenTelemetry SDK; Docker Compose sends traces to Jaeger, the private cluster to Tempo if it stays (D44), and elsewhere the exporter is off (`OTEL_TRACES_EXPORTER=none`). Settled 2026-11-20. | One trace ID per request ties the logs of every service together; a client must not choose our correlation ID. |
| D48 | Transactional outbox in the Debezium Outbox Event Router table shape (`aggregatetype` is the producer's topic, `aggregateid` the order ID), published by an in-process polling relay that takes a PostgreSQL advisory lock per batch, so one relay per service is active. Settled 2026-11-20. | The simplest relay, identical on every broker and without extra infrastructure; the table shape keeps change data capture open as the scaling path. |
| D49 | Delivery is at least once and unordered. Consumers are idempotent, tolerate reordering, and retry a missing prerequisite with backoff up to a limit before dead-lettering it: RabbitMQ quorum queues get a dead-letter exchange, an explicit delivery limit and at-least-once dead-lettering (`dead-letter-strategy=at-least-once`, `overflow=reject-publish`), and Kafka retries never block a partition. Queues, bindings and topics exist before producers run; RabbitMQ publishes are `mandatory`, so an unroutable message is a failure, and Kafka consumers start from the earliest offset. Settled 2026-11-20. | Competing consumers (KEDA), SQS Standard, retries and separate topics all reorder events; per-order ordering holds only within one Kafka partition or SQS FIFO message group and needs a single active consumer per RabbitMQ queue; unbounded retries stall partitions or silently drop messages. |
| D62 | Broker topology: Kafka has one topic per producing service (`orders`, `payments`, `inventory`) keyed by order ID; RabbitMQ has one topic exchange, the event type as routing key and one quorum queue per consuming service; SNS + SQS is laid out on Day 12 with raw message delivery, so consumers receive the same JSON. Each service may write only to its own topic or routing keys (Kafka ACLs, RabbitMQ topic permissions, SNS topic policies), and consumers accept each event type only from its producer's topic or routing key; on AWS, where raw delivery drops the topic, each subscription filters on `type` and each queue policy admits only the approved topics. Settled 2026-11-20. | The same envelope and keys on every broker; `source` is self-asserted, so the broker must stop one service from forging another's events. |
| D50 | Event catalogue v1: from order-api `order.placed`, `order.payment_failed` (consumed only by email-worker), `refund.requested`, `refund.completed` and `refund.failed` (consumed only by email-worker), every one that leads to a customer email carrying the customer's email and first name; from payment-api `payment.refunded` and `payment.refund_failed` (consumed only by order-api) and `payment.late_charge_refunded` (consumed by order-api and email-worker); from inventory `inventory.allocated` (one per order, with allocated and backordered quantities per line) and `inventory.backorder_allocated`. Settled 2026-11-20. | Each event comes from the owner of its facts; order-api owns refunds, so their details are published once; inventory and analytics act only on placed orders and skip the rest without storing or logging its payload. |
| D51 | Checkout saves the order as `pending_payment`, charges through payment-api with the order ID as idempotency key, then marks it paid and writes `order.placed` in one transaction: 201 paid, 402 declined, 202 still pending. A reconciler reads the charge's current state from payment-api and resubmits only when payment-api has no record of it; after 15 minutes unresolved, order-api asks payment-api to cancel the charge and follows its answer: a charge that already succeeded takes the paid path, a recorded cancellation fails the order, and an unanswered cancellation stays under reconciliation. An order that answered 202 and then fails emits `order.payment_failed`, so the customer is emailed; payment-api refunds any charge that succeeds after its cancellation and emits `payment.late_charge_refunded`. Settled 2026-11-20. | A crash or outage between charge and commit must neither lose a paid order, charge twice, nor keep money for a failed order; an idempotent replay may return a stale first response. |
| D52 | Stock is allocated asynchronously from `order.placed`, without reservation; shortfalls become first-in, first-out backorders, and goods receipts enter through an idempotent inventory API. Settled 2026-11-20. | A synchronous reservation adds coupling and a failure point to checkout. |
| D63 | Automatic replenishment: an (s, Q) reorder-point policy sends purchase orders to `supplier-simulator`, a simulated external supplier (#24). Settled 2026-11-20. | Load tests drain stock; a real shop restocks from its suppliers. |
| D53 | Refunds refine D13: within 30 days of payment, per line and quantity, requested with the order access token (D56); completed and in-flight refunds per line never exceed what was bought; VAT is returned proportionally: a refund's gross is the unit price times its quantity, its VAT is the line's VAT for the cumulative refunded quantity, rounded, minus the VAT already refunded, and its net is gross minus VAT, so the last unit takes every remainder; shipping is returned only when the whole order is refunded; requests on one order are serialised and return 202. order-api owns the saga and emits `refund.completed` once payment-api reports the money moved; inventory first cancels the line's open backorder and restocks only allocated units, assuming resellable returns. A refund unanswered between services is resent after 10 minutes, three times, then alerts; one pending at the provider for more than 5 days alerts; a final refusal emits `refund.failed`, so the customer is emailed, and alerts the team, which refunds by bank transfer with the customer's agreement and records it through an internal, idempotent order-api endpoint with no public route; order-api then emits `refund.completed` once, as for any refund. Settled 2026-11-20. | These are lab rules: 30 days counts from payment because fulfilment is out of scope, whereas the EU withdrawal period for goods runs 14 days from delivery; the EU 14-day reimbursement deadline bounds how long a refund may stay stuck. |
| D54 | Money is integer minor units with an ISO 4217 currency, EUR only. Prices include VAT; every order and refund line stores its rate and its net, tax and gross amounts, rounded per line, and totals are the sums of the lines and shipping. The shop is a fictitious German company charging 19 % German VAT on EU sales, valid below the EUR 10,000 yearly distance-sales threshold; the One-Stop Shop is a production gap. Analytics revenue is net of VAT. Settled 2026-11-20. | Retrofitting tax into a money model is expensive; per-line rounding with cumulative refund allocation never returns more than a line holds. |
| D55 | shipping-api quotes from rate cards by zone (`DE`, `EU-1` to `EU-3`), speed (standard, express) and weight band; order-api quotes server-side at checkout, with a timeout well inside the 500 ms checkout p95, and falls back to D14's flat rate on timeout or error. Settled 2026-11-20. | Prices from the browser are never trusted. |
| D56 | Guest checkout: the order access token is the HMAC-SHA-256 of the order ID under a key that order-api and email-worker read from Vault (Secrets Manager on EKS), so an idempotent replay returns it and the confirmation email carries a long-lived link to the order page without storing it. Links carry it in the URL fragment and the storefront sends it in a header; it never enters events, outbox rows, idempotency records or logs. Rotating the key invalidates every link. Settled 2026-11-20. | Order IDs leak through logs and URLs; a derived token survives a lost response and reaches the email without travelling through the broker. |
| D64 | Personal data: events carry only the customer's email and first name; every store (queues, retry and dead-letter queues, Kafka `retention.ms` plus `segment.ms`, published outbox rows) keeps an event for at most 7 days, and processing ends 7 days after the event's `time`, so a redrive never extends it; SNS retries towards an unavailable SQS queue are the one AWS exception. Among consumers only email-worker stores the contact, deleting it 60 days after payment or failure, or when the order's last backorder closes, whichever is later; an email whose contact is gone is not sent and alerts the team; analytics stores no personal data. Erasure on request is a production gap. Settled 2026-11-20. | Broker logs cannot erase single records; a contact must outlive the latest email it serves. |
| D57 | Shared code lives in `libs/go` (one module, linked by `replace`) and `libs/python` (installed editable). Go: `net/http`, `slog`, pgx, client_golang, amqp091-go, franz-go, google/uuid. Python: FastAPI and uvicorn (shipping-api only), psycopg, pika, confluent-kafka, prometheus_client, pydantic-settings. Both: the OpenTelemetry SDK with the OTLP exporter, and the AWS SDK when the SNS + SQS adapter arrives. No ORM. Migrations are goose SQL files run from the service image as a separate step under a schema-owner role, never at startup, with expand and contract for incompatible changes; services connect as a role that only reads and writes data. HTTP APIs live under `/v1` and return RFC 9457 problem details; mutating endpoints take an `Idempotency-Key` per the IETF draft (422 for a reused key with a different body, 409 while the original is in flight, 400 when missing; kept 24 hours); IDs are UUIDv7; timestamps are RFC 3339 in UTC. Settled 2026-11-20. | Shared code earns its place at the third consumer (D18); recorded library choices answer "why this one"; migrations at startup race between replicas and block rollbacks. |
| D58 | The storefront is static HTML and JavaScript served by unprivileged nginx, which also proxies `/api` in Docker Compose in place of the gateway. The fictitious catalogue holds laboratory and technical-office products, all at the standard VAT rate, a few of them low on stock. Settled 2026-11-20. | No frontend build to maintain; low stock produces backorders under load. |
| D60 | An order holds at most 50 lines of at most 99 units each, enforced at checkout and in the event schema; amounts stay at or below 2^53 - 1. Settled 2026-11-20. | An unbounded order makes an event larger than SNS accepts by default (256 KiB; at most 1 MiB when raised) and blocks the outbox behind it; larger integers lose precision in JSON parsers (RFC 7493). |

## Platform

| ID | Decision | Why |

| D20 | Private datacenter: Lima VM with nested KVM and libvirt, VMs created by Terraform; Multipass is the fallback. | Multipass networking passes only each VM's assigned IP, which breaks keepalived VIPs and MetalLB. |
| D21 | Private: 3 control planes, 3 workers, 2 load balancers. AWS: see D31. Amended 2026-11-19: AWS moved from kubeadm on EC2 to EKS. | A load balancer in front of a single API server balances nothing; three workers allow one replica per node for quorum tests. |
| D22 | Hybrid: the private cluster stays primary; burst nodes from an EC2 Auto Scaling Group join it over a WireGuard hub, with the Lima hypervisor VM as the private gateway, scaled by Cluster Autoscaler with short-lived join tokens; state stays private. Amended 2026-11-19: real elasticity replaces statically joined workers. | Capacity only while it is needed; teaches node networking, MTU and partitions. Stretching a cluster across a WAN is documented as a production anti-pattern. |
| D23 | Kubernetes 1.35, upgraded to 1.36 with kubeadm during the lab. | KEDA, Cilium and CloudNativePG support up to 1.36; the upgrade is a CKA-style drill. |
| D24 | Calico on the private cluster until Day 11, when a total-loss rebuild switches it to Cilium for the rest of the lab; AWS VPC CNI on EKS. Amended 2026-11-19: Cilium moved from AWS to the private rebuild. | Compare overlay/BGP, eBPF and VPC-native pod networking; Flannel cannot enforce NetworkPolicy. |
| D25 | Private edge: HAProxy + keepalived, MetalLB, Envoy Gateway, cert-manager with a local CA. AWS edge: ALB created by EKS Auto Mode from an Ingress, an ACM certificate for the cheapest available `labflow` domain (self-signed import as the fallback) and an AWS WAF rate-based rule, restricted to the learner's IP; ExternalDNS writes the record into the `baseline` hosted zone. Amended 2026-11-19: AWS edge added. | ingress-nginx is retired and archived; Envoy Gateway covers routing, TLS, rate limiting and JWT through the Gateway API; the AWS side contrasts a self-managed with a managed API edge. |
| D26 | Superseded 2026-11-19 by D31; the pending-`LoadBalancer` lesson moves to Day 5. | |
| D27 | Argo CD on the private cluster (private and hybrid scenarios); Flux on EKS; same deploy paths; one controller per cluster. Amended 2026-11-19: Flux runs on EKS. | Learn both tools without two controllers fighting over resources. |
| D28 | RabbitMQ with three nodes and quorum queues; Kafka with three KRaft nodes, replication factor 3, `min.insync.replicas` 2. | Kill one node and keep working; kill two and observe writes stop. |
| D29 | KEDA scales consumers on queue length and consumer lag, compared with a CPU-based HPA. | CPU is the wrong signal for queue workers. |
| D30 | CloudNativePG backups to S3 through the Barman Cloud plugin; point-in-time restore, and a full restore after the Day 11 total cluster loss; a periodic `pg_dump` to S3 is restored into RDS in the site-loss drill, measuring RPO and RTO. Amended 2026-11-19: physical Barman backups cannot be restored into RDS. | Replication is not a backup; a backup is proven only by a restore; cross-platform recovery needs logical dumps. |
| D31 | AWS scenario on managed services: EKS Auto Mode with a Graviton NodePool, RDS for PostgreSQL, ElastiCache for Valkey, SNS + SQS; edge, secrets, identity and observability in D25, D40, D41 and D44. Settled 2026-11-19. | Practise both stacks: operate the mechanism on the private cluster, buy it on AWS. AWS teams do not run kubeadm on EC2. |
| D32 | CloudFormation YAML for AWS: a retained, termination-protected `baseline` stack (buckets, the IRSA OIDC provider, the hosted zone, the deploy role, budgets; domain registration stays outside CloudFormation) and session stacks (network, cluster, data, messaging, hybrid) deployed through reviewed change sets and deleted after every session, ending with a check that only baseline resources remain; CI only lints them with cfn-lint and cfn-guard. Settled 2026-11-19. | AWS-managed state, change sets, rollback and drift detection; long-lived resources survive sessions; an ephemeral environment must not deploy on merge. |
| D33 | AWS network: two Availability Zones, private subnets and one NAT gateway, documented as a single point of failure. Settled 2026-11-19. | EKS needs two Availability Zones; one NAT gateway per zone is the production answer, one in total is the lab's cost choice. |

## Security and Operations

| ID | Decision | Why |
| --- | --- | --- |
| D40 | Vault + External Secrets Operator on the private cluster; AWS Secrets Manager + External Secrets Operator on EKS through Pod Identity, where the controller's role assumes a per-service role for each SecretStore and can therefore read every secret; etcd encryption at rest; operator-generated infrastructure credentials; no secrets in Git. Amended 2026-11-19: AWS secrets reach EKS through Pod Identity. | The application manifests stay identical; only the `SecretStore` changes. |
| D41 | Self-hosted IRSA (OIDC discovery in S3) on the private cluster; EKS Pod Identity on AWS; no IAM access keys; self-managed EC2 instances require IMDSv2 with a hop limit of 1. Amended 2026-11-19: EKS uses Pod Identity. | No long-lived cloud keys; avoids leaking the node role to every pod. |
| D42 | Human personas (admin, developer, oncall, auditor) through client certificates and RBAC groups; Dex/OIDC is a stretch goal. Per-service identities in every layer. GitHub Actions needs no AWS access today; a future workflow that does uses OIDC with a pinned `sub`. Cross-repository pull requests use a GitHub App token. API audit logging on. Amended 2026-11-19: CI no longer needs an AWS role. | Least privilege for people, workloads and automation. |
| D43 | Multi-arch images on GHCR built on native ARM runners, scanned with Trivy, signed with cosign keyless, deployed by digest; EKS pulls them from GHCR directly. Kyverno enforcement is a stretch goal. Amended 2026-11-19: no ECR pull-through cache, which would need a long-lived GitHub token. | What runs is provably what CI built. |
| D44 | kube-prometheus-stack; three SLOs (checkout success 99.5 %, checkout p95 under 500 ms, email within 60 s) with multi-window burn-rate alerts to Mailpit. On AWS, Amazon Managed Service for Prometheus evaluates the same rules and alerts through SNS, and CloudWatch covers managed services; the private Grafana shows both environments. Loki and Tempo are stretch goals. Amended 2026-11-19: AWS observability added. Amended 2026-11-20: Tempo is tried on the private cluster on Day 8 and kept if it fits once reservations follow measured usage; if memory is still short, it goes before Istio ambient (D59), and only once the learner has been told and agrees. A dead-letter queue that is not empty alerts, and a runbook redrives it before 7 days have passed since the event's `time`, discarding on sight anything older. | Alert on user impact, not on CPU. |
| D45 | k6 protocol-level user journeys from outside the cluster, plus one or two browser users; baseline, spike, soak, stress and mixed scenarios. | Browser automation does not scale to load testing; traffic must enter through the real edge. |
| D46 | AWS Paid plan from an "advanced" sign-up in `eu-central-1`, sign-up credits carried over; root MFA, a one-account AWS Organization with IAM Identity Center and no IAM access keys; budget alerts, Cost Anomaly Detection and a deny action back up a session-exit check; short sessions with session stacks deleted afterwards. Amended 2026-11-19: EKS Auto Mode needs instances outside the Free plan, which also removes its spending cap. | AWS is for proof, not for running all day. |
| D59 | Service-to-service traffic on the private and hybrid clusters uses Istio ambient mTLS (workload identities from ServiceAccounts) with AuthorizationPolicy allow-lists that also admit the gateway, Prometheus, KEDA and the operators, on top of default-deny NetworkPolicies that allow HBONE (15008) and the ambient probe address next to application ports. EKS relies on NetworkPolicies alone, with its network policy controller enabled, a documented difference. External callbacks carry an HMAC-SHA-256 over a timestamp and the raw body, checked in constant time within a tolerance window, with two valid secrets during rotation (D12, #24). Settled 2026-11-20; reopens the service-mesh exclusion. | Workload identity is the market standard and needs no application code; ambient mode avoids a sidecar per pod on a memory-bound host. |
